# Password recovery JSON API

Three CSRF-protected POST routes use Django's password-reset eligibility, token
generator, expiry/secret-fallback rules and `SetPasswordForm` validation:

| Route | JSON input | Success |
| --- | --- | --- |
| `/api/v1/auth/password-reset/` | `email` | 200 `{"accepted":true}` |
| `/api/v1/auth/password-reset/validate/` | `uidb64`, `token` | 200 `{"valid":true}` without consuming the token |
| `/api/v1/auth/password-reset/confirm/` | `uidb64`, `token`, `new_password1`, `new_password2` | 200 `{"password_reset":true,"login_required":true}` |

Bootstrap CSRF through the [session API](session-auth-api.md), then send JSON and
`X-CSRFToken` with the corresponding same-origin cookies. HTTP-only/session-backed
CSRF works. All input fields must be strings, with no query parameters or extra
body fields. JSON charset parameters are supported; forms/multipart/text are 415.
GET/HEAD do not request mail, validate links or change passwords and return 405.
Responses/errors are JSON, private/no-store, vary on Cookie and carry request IDs.
No NHL requests, new dependencies or schema migrations are introduced.

## Configure trusted email links

Set these server environment values before enabling JSON recovery requests:

```dotenv
PASSWORD_RESET_PUBLIC_ORIGIN=https://stats.example.com
DEFAULT_FROM_EMAIL=accounts@example.com
```

Replace the examples with your public origin and authorized sender. The existing
`EMAIL_BACKEND`, SMTP host/credentials and transport configuration control delivery.
`DEFAULT_FROM_EMAIL` is now environment-configurable, retaining Django's existing
`webmaster@localhost` default when omitted. The console backend remains useful for
development and prints the mail contents; tests use only the in-memory backend.

`PASSWORD_RESET_PUBLIC_ORIGIN` defaults to empty. Missing/unsafe configuration
returns 503 `password_reset_unavailable` for **every syntactically valid email**,
before matching accounts. The origin must have no credentials, query, fragment or
path other than `/`. HTTPS is required except DEBUG development loopback HTTP,
such as `http://localhost:8000`. No link origin is derived from request Host,
forwarded headers or body/query fields.

Keep `PASSWORD_RESET_FRONTEND_PATH` empty until the Vue build is actually served
at the configured trusted origin. The [Vue recovery routes](vue-password-recovery.md)
now exist, but their deployment activation is separate. Emails
then link to the existing HTML reset-confirm page under the configured origin,
which still completes the recovery workflow. Its Django token-to-session exchange
removes the raw token from the displayed form URL before rendering the form.

When activating the served Vue confirmation route, set its absolute path:

```dotenv
PASSWORD_RESET_FRONTEND_PATH=/recover-password/
```

The resulting link is `https://stats.example.com/recover-password/#uidb64=...&token=...`.
The fragment is not transmitted in the HTTP request. The Vue frontend reads it into transient memory, removes it from browser
navigation state before router creation and submits the API requests with JSON
bodies. Reloading the cleaned URL requires reopening the email link. Protocol-relative paths, backslashes, query or
fragment configuration are rejected. Existing HTML mail requests retain their
Django behavior; the trusted-origin rule above applies to the new JSON mail route.

## Request eligibility, privacy and delivery

The request uses `PasswordResetForm` email validation and `get_users()` matching.
Only active accounts with usable passwords receive instructions. Matching follows
Django's case-insensitive/Unicode-aware policy. Because registration does not make
emails unique, each matching eligible account gets its own link and account name.
Unknown, inactive and unusable-password addresses receive the same 200 acknowledgement
and no mail. No identity, UID, token, match count or delivery result appears in the
request response. Password/email/profile records are not changed by mail requests.

Mail is plain text; no HTML response/page is generated by the JSON API. Delivery
failures and zero reported messages are logged without exception text, addresses,
message bodies or tokens, and retain the same acknowledgement. `accepted` does not
prove account existence or successful delivery. Configuration failures are checked
uniformly before account lookup. Application diagnostics redact secrets; the chosen
mail backend still controls its own behavior, including console output in development.

Delivery is synchronous, like the current HTML flow. Uniform response bodies/statuses
provide response-level enumeration protection, **not a constant-time guarantee**:
SMTP and account matching can affect request duration. Asynchronous delivery and
rate-limiting policy remain deployment/security follow-ups before a public cutover;
this commit does not introduce a new queue or throttling system.

## Token validation and confirmation

Validation is optional and does not reserve or consume a link. Confirmation always
reloads the target user and rechecks active/usable-password status, token and expiry
while holding a PostgreSQL user-row lock. Unknown, malformed, oversized, expired,
used, wrong-account or invalidated links share 400 `invalid_reset_token` and a generic
message. Missing/wrong-type request fields use 400 `invalid_parameters`; empty or
oversized UID/token strings also receive the generic invalid-link error.

Django's configured `PASSWORD_RESET_TIMEOUT` and `SECRET_KEY_FALLBACKS` remain
authoritative. Password, email or last-login changes invalidate tokens according
to Django's generator. Deactivated/unusable accounts are refused at use time too.
No new bearer-token persistence table or calendar/identity guessing is introduced.

Both new password fields are required. Django's confirmation/strength/similarity
rules apply to the freshly loaded user, and exact password whitespace is preserved.
Field errors do not consume a token. User/password/profile signal writes are atomic;
a failed save rolls back the password and leaves the link usable. Even resetting
to the same password creates a new salted hash and invalidates the old token.

The API and existing HTML confirmation share that service. Simultaneous submissions
in either direction cannot both reset the password: the loser rechecks the updated
user after acquiring the lock and sees an invalid token. HTML preserves its normal
form/error/complete-page behavior and does not automatically log in.

Successful API confirmation also requires a separate login. Existing target sessions
become invalid on their next Django authentication check; no fresh login is created.
Another signed-in account's caller session and owned data remain intact. Rediscover
session state and bootstrap CSRF before the next login/private request, especially
with session-backed CSRF. A separate profile-edit fix saves only its declared
username/email fields, so a stale profile form cannot restore an old password or
last-login snapshot after the reset.

## Errors and regression scope

Wrong password/UID/token values are never echoed. Invalid input is 400, missing or
bad CSRF/origin is 403 `csrf_failed`, unsupported methods 405, HTML negotiation 406,
non-JSON bodies 415 and unsafe/missing mail destination configuration 503. Unexpected
server failures keep the generic API 500 response. Link/password fields are write-only
where secret in OpenAPI; request paths contain no reset UID/token.

Synthetic PostgreSQL tests cover complete API and HTML flows, eligibility/privacy,
multiple matching accounts, trusted origin/fragment configuration, delivery failures,
secret fallback, expiry/reuse, password validation, session invalidation, stale profile
writes, rollback and real concurrent API/HTML token consumption in both directions.
All test mail is captured in memory. Implementation under `users`/`nhl_web_app.api`
is tested explicitly outside the unchanged `players` coverage scope. Private owned
resources and account-editing APIs remain later migration work.
